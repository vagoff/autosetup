## Инструмент версии БСП

```
AUTOSETUP_PROFILE=data/profiles/win11-1c.json5 node src/tools/read-1c-subsystem-versions.js
```

Читает регистр сведений `ВерсииПодсистем` через внешнее соединение и печатает версию конфигурации, поставщика и версии **всех** встроенных библиотек, включая `СтандартныеПодсистемы` — это единственный достоверный источник версии БСП, номер релиза конфигурации о ней не говорит ничего.

Сделал его сразу и тестом, как вы и предложили. Две вещи, которые делают его не просто принтером:

- **Проверяет мою непроверенную гипотезу.** Он вызывает объявленный в конфиге `РегламентныеЗаданияСервер.РаботаСВнешнимиРесурсамиЗаблокирована()` — это getter без побочных эффектов, поэтому дёргать безопасно. Если метода под таким именем нет, скрипт падает с точным текстом COM-ошибки. Тот самый риск, о котором я предупреждал, теперь ловится наблюдаемо и **до** того, как на имя понадеется модуль блокировки.
- **Не угадывает имена колонок регистра.** Они у БСП разных версий разъезжаются, поэтому он берёт `ВЫБРАТЬ *` и ищет строку, где значение совпадает с `СтандартныеПодсистемы`, а версию — по форме `N.N.N`. Никакой завязки на конкретное имя поля.

## Побочный результат смены локали

Консоль гостя теперь CP866, и кириллица в stdout приходила мусором. Перевёл COM-модули на base64 UTF-8 — тем же приёмом, что уже был в `run-1c-query.ps1`. Это стоит иметь в виду для всех будущих guest-скриптов: **текстовый stdout из гостя больше не безопасен для данных**.


Канонический инструмент — `run-1c-query.js --documents-top`: серверная процедура в EPF (`ПосчитатьДокументыНаСервере`) сама перебирает `Метаданные.Документы` и делает `ВЫБРАТЬ КОЛИЧЕСТВО(*)` по каждому типу **на сервере**, без сетевых round-trip'ов. ## Программная проверка прав роли: `ПравоДоступа()` -- ГЛОБАЛЬНАЯ функция, не метод объекта роли

Нужно было (см. `features/1c-odata-publisher`, `ПроверитьПраваРолей`) сверять `rights`/`catalogRights` из `data/1c-odata.json5` с тем, что реально дают назначенные статические роли -- программно, без реальной попытки записи.

Первая попытка звала это как метод: `РольМетаданных.ПравоДоступа("Чтение", ОбъектМетаданных)` -- рантайм-ошибка "Метод объекта не обнаружен". Причина проста и обидна: **`ПравоДоступа` -- функция ГЛОБАЛЬНОГО контекста, а не метод роли**. Правильный вызов:

```bsl
ПравоДоступа(<Право>, <ОбъектМетаданных>, <РольИлиПользователь>)
```

где `<Право>` -- строка (`"Чтение"`/`"Добавление"`/`"Изменение"`/`"Удаление"`), а необязательный третий параметр -- либо `Метаданные.Роли.<Роль>` (проверить именно эту статическую роль), либо `ПользовательИнформационнойБазы` (проверить совокупные права пользователя от всех его ролей, без входа под ним). Английские имена: `AccessRight`, права `Read`/`Insert`/`Update`/`Delete`. Официальный источник: [стандарт 1С "Verifying access rights"](https://kb.1ci.com/1C_Enterprise_Platform/Guides/Developer_Guides/1C_Enterprise_Development_Standards/Setting_data_access_rights/Verifying_access_rights/).

Важные условия по этому же стандарту:
- при явном третьем параметре (роль/чужой пользователь) выполняющий проверку сеанс должен иметь административные права -- у нас так и есть (`database.userName` из `data/1c-configuration.json5`, тот же администратор, что везде в автоматизации);
- не делать такую проверку в привилегированном режиме (`УстановитьПривилегированныйРежим(Истина)`) -- тогда `ПравоДоступа()` может безусловно вернуть `Истина`;
- начиная с режима совместимости 8.3.10 несовместимые Право/ОбъектМетаданных бросают исключение, а не возвращают `Ложь`.

Отдельно есть `ПараметрыДоступа(Право, ОбъектМетаданных, СписокПолей, РольИлиПользователь)` (`AccessParameters`) -- отвечает, есть ли у права RLS-ограничение (`Доступность`/`ОграничениеУсловием`), но НЕ текст самого RLS-условия и не ответ "можно ли изменить вот эту конкретную запись". Мы это не используем: `ПравоДоступа()` достаточно для базового CRUD-аудита состава `rights`/`catalogRights`, а окончательная проверка конкретной записи под RLS BAS ERP -- это уже реальная операция через OData (см. `features/odata-demo`, живая проверка `PATCH` поймала до этого реальное несоответствие `rights` факту).

Живой прогон `node src/verbs/publish-1c-odata.js` подтвердил: недостающих прав нет (иначе была бы фатальная ошибка), а `warnings` честно перечисляет реальный избыток -- например, `Документ.ДоступностьРабочихЦентров: assigned roles also grant 'update'` -- ровно то расхождение, которое раньше пришлось ловить вручную живым `PATCH` через OData.

Побочная находка при отладке: глобальная `РольДоступна("ИмяРоли")` (проверяет ТЕКУЩЕГО пользователя текущей сессии, не принимает объект метаданных) в нашем headless-запуске (`1cv8c.exe ENTERPRISE .../Execute ... /N admin /P ""`) зависала на 240+ секунд без исключения и без результата. Она нам для этой задачи не нужна (нужен был именно `ПравоДоступа()` с ролью третьим параметром), поэтому решили не разбираться дальше -- но если где-то ещё понадобится `РольДоступна()`/`IsInRole()` из headless EPF, сначала проверьте её изолированно, не считайте рабочей по умолчанию.

## COM-коллекция колонок результата запроса не поддерживает `Count()`/`Get(i)`

`РезультатЗапроса.Колонки` через `V83.COMConnector` (используется в `run-1c-external-query.js` для произвольных запросов) — это COM-объект, у которого:

- `.Count()` падает: `does not contain a method named 'Count'`;
- `InvokeMember("Количество", ..., GetProperty/InvokeMethod, ...)` падает: `DISP_E_UNKNOWNNAME` — то есть у коллекции нет вообще ни английского, ни русского именованного метода счёта/доступа по индексу.

Коллекция при этом реально доступна: она реализует стандартный `IEnumVARIANT`, и `foreach ($column in $columnCollection) { ... }` в PowerShell читает её штатно. Это НЕ баг конкретного вызова — свойство `Колонки` у `ВалueTable.Unload()` (после `Unload()`) неожиданно ведёт себя иначе: `Get1C` возвращает уже смаршалленный `System.Object[]`, с рабочим `.Count`/индексатором. Но у самого `РезультатЗапроса.Колонки` (без `Unload()`) — нет. Разные типы, разное поведение, диагностировано живыми пробами (см. `git log` по `src/infrastructure/build-1c-com-query-script.js`). Фикс — `build-1c-com-query-script.js` использует `foreach`, не `Count()`/`Get(i)`.

## Мелочи

- стоит иметь в виду для всех будущих guest-скриптов: текстовый stdout из гостя больше не безопасен для данных.
- `probeTimeoutSeconds` в `data/1c-query-runner.json5` — не про сложность запроса. Холодный тонкий клиент на большой production-копии ИБ стоит ~30-40с ещё до выполнения самого запроса (просто открыть ИБ). Не срезайте этот таймаут "для скорости" не измерив живым запуском.
- через COM в этой версии Метаданные.НайтиПоПолномуИмени() возвращает null, хотя объект существует. Это отличие COM-обёртки, не отсутствие OData.
- Windows PowerShell 5 читает UTF‑8 без BOM как ANSI, поэтому кириллица разрушает синтаксис. Это тоже подтверждает правило проекта о гостевой кодировке.
- COM различает типы метаданных не так, как BSL: список ролей читается, а каталог документов возвращается в иной marshalled-форме.
