## что нужно сделать

генеральная цель:

получить windows и 1c environment в qemu с загруженной копией инфобазы с продакшена для отладки и экспериментов.
все скрипты пишем или на nodejs (которые будут исполняться локально) или на PowerShell (которые будут засылаться в windows)
или на OneScript (которые нужны для управления 1C).

что больше всего беспокоит на данный момент:

настроенная windows и 1с чтоб можно было зайти проверить вручную.

## как нужно сделать

принципы:

- **FULLAUTO**. строгое отсутствие интерактива или вообще любых неавтоматизированных шагов в процессе создания окружения.
  процесс должен быть скриптован и воспроизводим от начала до конца.
- **SRP**, **DRY**. все скрипты должны быть модулярные и строго подчиняться принципам SRP и DRY.
- **MODULAR** один скрипт должен выполнять одно ограниченное действие, не писать больших пакетов которые негибко делать все сразу.
- **FULLCONF**. протяжка всего конфига от начала до конца, без размазанных там и сям локальных конфигов или defaults.
  еще раз: зашитые defaults внутри скриптов, это нарушение принципа -- все конфиги должны быть в одном месте!
- **MODULE-GRANULARITY**. один скрипт = одно проверяемое действие
  (одна проверка / одна генерация файла / один запуск процесса).
  Если для результата нужно несколько действий — это отдельный
  тонкий оркестратор, который только вызывает модули по порядку
  и не содержит собственной логики.
- **NAMING-BY-VERB**. имена скриптов — глагол+объект одного действия
  (check-kvm-device.js, build-answer-file.js, create-disk-image.js,
  spawn-qemu-process.js), а не имена фаз/этапов (preflight.js,
  launcher.js). Имя-фаза почти всегда сигнализирует, что внутри
  свалено несколько обязанностей.
- **CONFIG-SINGLE-SOURCE**. константы (пути, размеры, версии, URL,
  cpu/ram, списки пакетов) объявляются один раз в едином
  конфиг-модуле и импортируются везде, а не инлайнятся в
  скриптах-исполнителях.
- **ANTI-BLOAT** (уточнение). декомпозиция — это простые функции с
  чётким вводом/выводом, без классов/фреймворков/слоёв ради слоёв.
  Модульность не равно энтерпрайз.
- **NOSHELL**. скрипты пишем на нормальных человекочитаемых языках и проектируем тщательным образом.
- **NOEXTRAMD**. не читай из папок `<projectroot>/doc/{tasks,fragments}`, `<projectroot>/{memo,garbage}` чтобы не замусоривать контекст, там лежат или потерявшие актуальность исторические документы или части системы управления контекстом на мета уровне.
- **NOHIDEBUG**. не заметаем баги под коврик, разбираемся каждый раз до конца.

требования:

- генеральный конфиг пишем в JSON5.
- соединения делаем по tcp, не по unix sockets. исключение -- локальный unix-сокет для swtpm↔qemu ctrl-канала, потому что там иначе не работает.
- для агента не забываем открыть qemu console для управления по tcp.
- человеку оставляем возможность ходить на qemu по spice и по vnc для проверки и экспериментов, выбор через конфиг, по умолчанию spice.
- у alpine и obarun общее сетевое пространство, никаких "портов" никуда "пробрасывать" не нужно.
- для скриптов которые нажимают кнопки время не подгадываем делаем детерминированно!
- также при установке windows и софта под него следует избегать очень специфичных хаков чтобы процесс не зависел от свойств конкретных версий конкретных программ.
- create-скрипты для stateful-ресурсов (диск/OVMF vars/tpm state) обязаны fail-fast, а не молча пропускать/перезаписывать.
- делать установку разных необязательных для windows фич отдельными модулями. например установка всего нужного для того чтобы обеспечить вход по ssh и вход по rdp
  (десктоп сессию) пример двух таких модулей.
- кириллицу не пишем в выводе скриптов, она на windows превращается в `?????`.

архитектурные решения:

- вся связь — tcp/loopback (TPM ctrl-канал 127.0.0.1:4001, QMP 127.0.0.1:4000,
  SPICE 127.0.0.1:5900/VNC 127.0.0.1:5901), unix-сокеты нигде не используются.
- экран человеку: SPICE по умолчанию (буфер обмена, ресайз), VNC — альтернатива,
  переключение через `qemu.displayProtocol` в конфиге. `-display none` +
  `-vga qxl` — никаких локальных GTK/SDL-окон (это служба, не десктоп-процесс).
- диск — SATA/AHCI, не virtio: сознательно, чтобы не тащить virtio-win
  driver ISO на этапе установки. Можно пересмотреть после первой установки.
- сеть гостя — e1000e + SLIRP hostfwd 2222→22 (ssh), 5985→5985 (winrm).
  RDP-проброс сделан и убран — не нужен для "зайти проверить руками"
  (это закрывает SPICE/VNC), понадобится отдельно только если решим
  включать Remote Desktop сервис внутри гостя PowerShell-скриптом.
- argv qemu проверен структурно на заглушках файлов (в песочнице нет
  /dev/kvm и не установлен qemu — реальный запуск не тестировался).

## что имеем на данным момент

пути:
- константные конфиги и таблицы и образы писать сюда `/data/wd/aibox/autosetup/data`.
- базы данных и образы r/w дисков сюда `/data/wd/aibox/autosetup/db`.
- discardable данные сюда `/data/wd/aibox/autosetup/cache`.
- скрипты для само обслуживания кладем в `/data/wd/aibox/autosetup/scripts/`.
- скрипты которые выполняют задачу в `/data/wd/aibox/autosetup/src/`.

инструменты для агента (в `scripts/`, не для человека):
- `scripts/run-qmp-command.js <command> [argsJSON]` — разовая произвольная QMP-команда
  (query-status, query-block, query-blockstats, quit, send-key, ...) поверх уже
  существующего `src/lib/connect-qmp.js`, JSON-ответ в stdout. Завёлся вместо
  повторяющихся одноразовых `node -e "..."` в ручной диагностике по QMP.
  Пример: `node scripts/run-qmp-command.js query-status`.
- `scripts/shutdown.sh` — только для человека на хосте: убивает qemu по
  `qemu.pidFile` и подтверждает смерть процесса. Из sandboxed-контейнера агента
  НЕ РАБОТАЕТ для реального qemu — PID-namespace не расшарен с хостом (расшарена
  только сеть), поэтому `process.kill(pid, 0)` внутри контейнера всегда "никого
  не находит", даже если на хосте процесс жив. Агенту для остановки VM — только
  QMP `quit` по сети (`node scripts/run-qmp-command.js quit`), не PID-based kill.

сохраненные пакеты для чтения и анализа:
- `/data/wd/aibox/autosetup/_vendor/v8runner`
- `/data/wd/aibox/autosetup/_vendor/vanessa-runner`
- `/data/wd/aibox/autosetup/_vendor/1cmgmt.1.2.3.nupkg`
(если что-то клонить то через `git git clone --depth 1 --single-branch xxx`)

среда: host = obarun linux, agent's container = alpine linux (musl), всё на одной машине с общей сетью, alpine в bwrap контейнере с `--unshare-all` и `--share-net`,
если что-то ножно доставлять или редактировать в системе (obarun или alpine) надо записывать в виде скрипта и исполнять,
а не редактировать состояние систеемы, чтобы все было легко воспроизводимо в будущем.

QEMU и скрипт создания vm образов работает на host машине человека, если агенту надо их запустить, пусть просит человека.

памятка:
- Node ≥22 используется ради встроенного `zlib.crc32` в `ppm-to-png.js` (там же — самодельный PNG-энкодер без зависимостей).
