Тут неприятный ответ: стандартный OData не даёт симметричной блокировки «кто открыл первым — тот редактирует». Он обеспечивает только контроль уже записанной версии через `DataVersion` + `If-Match`.

Критическая тонкость: «документ открыт» и «пользователь уже начал его изменять» — разные состояния. Платформа ставит пессимистическую блокировку формы только после первого интерактивного изменения, а не при открытии. При этом программная запись, к которой относится OData, способна пройти мимо объектной блокировки формы — это не долгоживущий SQL-lock. [Описание поведения форм 1С](https://its.1c.ru/db/content/metod8dev/src/platform81/metod/form/i8102880.htm).

### 1. Документ открыт в 1С → что делает веб

| Состояние в 1С                     | PATCH из веба                                         | Что затем увидит пользователь 1С                                                                    |
| ---------------------------------- | ----------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Форма только открыта               | Успешно                                               | При попытке начать редактирование форма обнаружит изменившуюся версию и потребует перечитать данные |
| Пользователь уже изменил поля      | PATCH всё равно может пройти                          | При записи пользователь получит конфликт версии: данные изменены другим сеансом                     |
| Пользователь уже записал изменения | С правильным старым `If-Match` веб получит HTTP `412` | В 1С всё нормально; конфликт обрабатывает веб                                                       |
| И веб не передал `If-Match`        | PATCH запишет поверх текущей версии                   | Возможна потеря изменений, особенно при полной замене табличной части                               |

То есть даже если пользователь 1С уже набрал половину документа, но ещё не записал его, `DataVersion` в базе остаётся прежней. Веб передаст совпадающий `If-Match`, успешно запишет документ, а конфликт прилетит затем пользователю 1С.

### 2. Документ открыт в вебе → что делает 1С

Сам факт GET и открытой HTML-формы ничего в 1С не блокирует. OData stateless: HTTP-запрос закончился — никакого «сеанса редактора» в 1С больше нет.

Последовательность получается такая:

1. Веб читает документ и сохраняет `DataVersion = V1`.
2. Пользователь 1С открывает, редактирует и записывает документ.
3. Версия становится `V2`.
4. Веб отправляет `PATCH` с `If-Match: V1`.
5. 1С отвечает `412 Precondition Failed`.
6. Веб должен показать конфликт и предложить перечитать/смержить изменения.

Именно так 1С документирует `If-Match`: если переданный `DataVersion` уже не совпадает, модификация не выполняется и возвращается `412`. [Документация по оптимистической блокировке OData](https://42clouds.com/ru-ru/manuals/interfeys-odata-primery-tipovykh-operatsiy/).

Но если пользователь 1С ещё только редактирует и не записал, версия всё ещё `V1`, поэтому веб сохранится первым, а конфликт получит 1С.

### Практический вывод

Со стандартным OData нормальная стратегия только такая:

* веб при загрузке сохраняет `DataVersion`;
* любой `PATCH` и `DELETE` обязательно отправляет `If-Match`;
* при `412` веб перечитывает объект и показывает конфликт;
* при master-detail веб хранит исходную и изменённую версии строк, потому что табличную часть приходится передавать целиком;
* автоматического last-write-wins быть не должно.

Это защищает от тихого затирания уже записанных данных, но не создаёт эксклюзивного редактора.

Если требуется именно:

> открыт в вебе → 1С не позволяет редактировать; открыт в 1С → веб становится read-only,

то стандартного OData недостаточно. Нужны расширение конфигурации и собственный lease-механизм: регистр блокировок `{Объект, Владелец, Канал, Token, ExpiresAt}`, heartbeat из веба и проверки в формах/`ПередЗаписью`. Причём веб-запись тогда лучше проводить через собственный HTTP-сервис с lock-token, а OData оставить для чтения. Держать настоящую объектную блокировку 1С между stateless HTTP-запросами практически невозможно и архитектурно вредно.

## Ревизия (2026-08-28): что нашлось при прицельном поиске способов

Задача сессии — именно поискать пути решения, не переизобретая то, что уже
исследовано выше. Три направления поиска и их результат.

### 1. Живая ИБ: нет ли в BAS ERP персистентной блокировки редактирования

Через `V83.COMConnector` от имени `Администратор` (в обход ограниченных прав
`autosetup-odata`) прочитан полный список регистров сведений конфигурации
(557 штук) в поиске БСП-подсистемы «Предотвращение редактирования объектов
несколькими пользователями» (aka object locking / pessimistic edit lock).

Результат: **такого регистра в составе метаданных нет**. Есть похожие по
названию, но не по смыслу: `БлокировкиСеансовОбластейДанных`,
`БлокировкиСкладскихЯчеек`, `БлокировкиПооперационногоРасписания` — блокировки
других предметных областей, не редактирования объектов. Есть константа
`СведенияОБлокируемыхОбъектах`, но она типа ХранилищеЗначения и по паттерну
БСП — это кеш метаданных о том, какие типы вообще поддерживают
объектные блокировки, а не сами блокировки; в любом случае это не регистр,
хранящий активные блокировки.

Вывод объясняет исходную теорию из первой части документа документально: 1С
держит пессимистическую блокировку формы объекта **в памяти кластера
сервера**, в рамках интерактивного сеанса (см. ту же ссылку на
`its.1c.ru/db/content/metod8dev/.../i8102880.htm` выше). Она никогда не
попадает ни в одну таблицу СУБД и поэтому принципиально не видна ни через
OData, ни через прямой SQL/COM-запрос. Stateless HTTP-интеграция физически
не может ни увидеть такую блокировку, ни поучаствовать в ней — не потому что
не реализовано, а потому что механизму нечего показать наружу.

### 2. Есть ли способ показать пользователю веба не «всё переписать», а diff

Проверен альтернативный путь: БСП-подсистема версионирования объектов
(`РегистрСведений.ВерсииОбъектов`, хранит `ВерсияОбъекта` — `ХранилищеЗначения`
с сериализованным снимком объекта на момент записи). Если бы она была
заполнена, из неё в принципе можно было бы вытащить «версия на момент
открытия формы в вебе» и показать честный постатейный diff вместо слепого
«перечитано, начните заново».

Проверено запросом (`Администратор`, напрямую к регистру): **в этой копии
регистр пуст** (`SELECT COUNT(*) = 0`) — версионирование объектов в BAS ERP
на этом стенде не включено ни для одного из пяти документов демо. Даже если
бы было включено, `ВерсияОбъекта` — это внутренний бинарный формат сериализации
1С (compressed XML), для которого нет открытого недокументированного парсера
на PHP-стороне; разбирать его самодельным кодом — ровно тот костыль, который
запрещён требованиями проекта. Путь закрыт по обеим причинам: и практической
(не включено), и принципиальной (пришлось бы поддерживать закрытый формат).

### 3. Что делают чужие интеграции — совпадает ли наш выбор с консенсусом

Прогреплены все проекты из `vendor/`: `1c-odata` (hacker-cb, современный
TS-клиент), `onec-odata` (Python), `odata-1c` (kilylabs), `odata-1c-php`
(mihpa), `odata1c-client` (Dakword), `metadata.js`.

Важная независимая находка в `vendor/1c-odata/packages/client/src/concurrency.ts`
и `errors.ts` (открытый исходный код, актуален на 2026 год, не наш стенд):

> «Spec §2.5: 1С silently ignores the `If-Match` header, so optimistic
> concurrency must be enforced client-side.»

Это дословно то же самое, что задокументировано выше в `deferred-todo.md` по
результатам наших собственных `curl`-тестов — только это уже не гипотеза про
конкретный билд нашего стенда, а задокументированное поведение платформы,
подтверждённое независимо третьим проектом. Библиотека реализует ровно ту же
защиту, что уже есть у нас в `runtime_lib.js#odatatest_update_entity()`:
GET непосредственно перед записью, сравнение `DataVersion` на своей стороне,
синтетическая ошибка конфликта при расхождении (`ConcurrencyError`), `If-Match`
отправляется по инерции (безвреден, сработает, если платформу когда-нибудь
починят). Ни один из остальных пяти проектов не предлагает ничего более
сильного — `onec-odata`/`odata-1c`/`odata-1c-php` просто транслируют
`If-Match` в заголовок, доверяя документации 1С буквально, без собственной
проверки (то есть на этой платформе их защита реально не работает вообще).
Ни в одном проекте нет ни pessimistic-lock, ни checkout/lease поверх
стандартного OData — вывод из первой части документа («это архитектурно
недостижимо без расширения 1С») независимо подтверждён отсутствием
контрпримеров.

### Итог поиска

Ничего сильнее уже реализованного в демо найти не удалось — и не потому что
плохо искали, а потому что для этого нет данных: ни в СУБД, ни в открытом
клиентском коде других интеграторов. Текущая защита демо (перечитать
`DataVersion` прямо перед `PATCH`, отклонить и попросить перечитать при
расхождении) — это ровно тот максимум, который единодушно выбирают независимые
клиенты 1С OData как класс. Единственный способ получить настоящую
взаимоисключающую блокировку — свой HTTP-сервис в расширении конфигурации
(см. вывод в конце первой части документа); это осознанно вне рамок демо.

Что можно было бы сделать в демо *в рамках уже выбранной стратегии*, но не
сделано, потому что это UX-полировка, а не новый способ решения конфликта:
при конфликте сохранять то, что пользователь успел ввести (сейчас форма
после конфликта показывает свежие данные из 1С, а не черновик пользователя),
чтобы не заставлять перепечатывать правки вручную.
