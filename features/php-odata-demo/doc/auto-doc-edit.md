Коротко: готового живого виджета формата «указал URL `standard.odata` → получил полноценный редактор любых документов 1С» я не нашёл.

### Почему одного `$metadata` недостаточно

Стандартный интерфейс 1С действительно позволяет получить метаданные и выполнять создание/редактирование/удаление; при этом 1С использует OData V3. [Официальное описание 1С](https://1c-dn.com/1c_enterprise/rest_interface/)

Но `$metadata` описывает преимущественно структуру данных:

* имя сущности и полей;
* тип `Edm.String`, `Edm.Decimal`, `Edm.DateTime`;
* ключи и связи;
* nullable и размеры;
* коллекции и табличные части.

Там нет полноценного описания формы 1С:

* порядка и группировки полей;
* условной видимости;
* пользовательских представлений;
* вариантов выбора ссылок;
* зависимостей между полями;
* команд «Провести», «Отменить проведение», «Заполнить»;
* серверных проверок и обработчиков;
* поведения блокировок.

Поэтому автоматически можно получить хороший технический CRUD-редактор, но не точную копию формы документа 1С.

### Что я бы использовал для PHP-only

Node на сервере для этого не требуется:

```text
1С OData V3
     ↓
PHP proxy + parser $metadata
     ↓
JSON Schema + UI Schema
     ↓
JSON Forms в браузере
     ↓
PHP adapter → POST/PATCH в 1С
```

[JSON Forms](https://jsonforms.io/docs/renderer-sets) уже умеет автоматически выбирать редакторы для строк, дат, чисел, перечислений, объектов и массивов. Для табличной части есть готовые варианты «таблица» и [list-with-detail](https://jsonforms.io/examples/list-with-detail).

Поверх него потребуются 1С-специфичные renderers:

* ссылка на справочник → autocomplete/selector;
* перечисление → dropdown;
* табличная часть → editable grid;
* `Ref_Key` и `DataVersion` → скрытые системные поля;
* `DeletionMark`, `Posted` → специальные индикаторы;
* составной тип → выбор типа плюс значения;
* команды проведения → отдельные кнопки OData;
* конфликт `DataVersion` → диалог «объект был изменён».

Практически разумная модель — не «ноль настроек», а:

1. 80–90% формы генерируется из `$metadata`;
2. поверх накладывается небольшой JSON/YAML override:

```json
{
  "Document_ЗаказПокупателя": {
    "title": "Заказ покупателя",
    "hidden": ["Ref_Key", "DataVersion", "DeletionMark"],
    "groups": {
      "Основное": ["Date", "Number", "Контрагент_Key", "Склад_Key"],
      "Дополнительно": ["Комментарий", "Ответственный_Key"]
    },
    "tables": {
      "Товары": {
        "columns": ["Номенклатура_Key", "Количество", "Цена", "Сумма"]
      }
    }
  }
}
```

Это останется динамическим: новый реквизит появится автоматически, а override нужен только для приличного UX.

Итог: `metadata.js` — наиболее близкий 1С-специфичный проект, но не прямой редактор стандартного OData. Для вашей PHP-only схемы наиболее реалистична связка **PHP OData adapter + `$metadata` → JSON Schema + JSON Forms**. Отдельно всё равно придётся реализовать ссылки, табличные части, проведение и optimistic locking через `DataVersion`.
