# Отложенное и упёршееся

## OData отдаёт 500 на `Document_ПоступлениеТоваровУслуг` (блокирует документ в демо)

Обнаружено при проверке PHP-клиента на живом стенде (2026-08-27).

Четыре из пяти документов из `data/1c-odata.json5#rights` читаются нормально:

| Документ | `/$count` | страница `$top=5` |
|---|---|---|
| ДоступностьРабочихЦентров | 140, 0.03 с | 5 строк, 0.46 с |
| ВыпускПродукции | 84, 0.13 с | ок |
| ЗаказПоставщику | 82, 0.15 с | ок |
| МаршрутныйЛистПроизводства | 87, 0.11 с | 5 строк, 0.03 с |
| **ПоступлениеТоваровУслуг** | **HTTP 500** | **HTTP 500** |

Ответ 1С (`$format=json`):

```json
{"odata.error": {"code": "-1", "message": {"lang": "uk", "value": "Помилка виконання запиту"}}}
```

Что уже проверено:

* падает даже `?$top=1&$select=Ref_Key` -- то есть дело не в сериализации
  конкретного реквизита, а в самом объекте;
* все пять справочников из `catalogRights` (включая RLS-нагруженных
  Контрагентов) читаются без ошибок -- значит публикация и пользователь целы;
* тип присутствует в `$metadata` и попал в `data/dbinfo.json` (82 реквизита,
  4 табличные части), то есть в состав OData он включён.

Рабочая гипотеза: RLS (ограничение доступа на уровне записей) роли
`ЧтениеПоступленийТоваровУслугВозвратовПоставщикам` в BAS ERP. Роли выданы
пользователю напрямую, без групп доступа и значений доступа, поэтому шаблон
RLS не может вычислиться, и запрос падает уже на выполнении.

Как проверять дальше (не сделано):

1. `ПараметрыДоступа("Чтение", Метаданные.Документы.ПоступлениеТоваровУслуг, <пользователь>)`
   -- покажет, есть ли у права RLS-ограничение; сравнить с тремя рабочими
   документами (см. `doc/1c-notes.md`, там же предупреждение про
   привилегированный режим);
2. журнал регистрации 1С -- там должен быть развёрнутый текст ошибки;
3. если гипотеза верна -- либо завести пользователю группу доступа со
   значениями доступа, либо убрать документ из `rights`.

До выяснения документ остаётся в `rights` (право `read`/`update` заявлено),
но в конфиге генератора демо-страниц его включать нельзя -- страница списка
будет падать на первом же запросе.

## 1С игнорирует `If-Match` — документированная оптимистическая блокировка не работает

Обнаружено при проверке карточки документа (2026-08-27), перепроверено
корректной методикой после консультации.

### Что обещает документация

Руководство разработчика («Оптимистическая блокировка данных», раздел есть
и в 8.3.6, и в 8.3.27): прочитать `DataVersion`, передать его в `If-Match`
при `PATCH`/`DELETE`; при несовпадении текущей версии операция НЕ выполняется
и возвращается **HTTP 412**.

* https://its.1c.ru/db/v836doc/bookmark/dev/TI000000783
* https://its.1c.ru/db/v8327doc/bookmark/dev/TI000000783
* https://kb.1ci.com/1C_Enterprise_Platform/Guides/Developer_Guides/1C_Enterprise_8.3.23_Developer_Guide/Chapter_17._Integration_with_external_systems/17.4._Standard_OData_interface/17.4.13._Performing_standard_operations/

### Что происходит на стенде

Первая проверка была НЕКОРРЕКТНОЙ: в `If-Match` уходила произвольная строка,
а платформа вправе трактовать нераспознанное значение как отсутствующее.
Правильный CAS-тест голым curl (без PHP-обёртки):

```
1) D0 = AAAAEwAAAAA=
2) PATCH  If-Match: D0 (актуальный)          -> HTTP 200,  D1 = AAAAFAAAAAA=
3) PATCH  If-Match: D0 (НАСТОЯЩИЙ устаревший) -> HTTP 200   <-- ожидался 412
4) контроль: Комментарий = "НЕ ДОЛЖНО ЗАПИСАТЬСЯ"
```

Шаг 3 — ровно документированный сценарий, и он не работает: запись применена,
чужие изменения затёрты.

Транспорт исключён: `curl -v --http1.1` показывает `If-Match: AAAAEwAAAAA=`
на проводе, без кавычек и без `W/`; между curl и 1С только проброс порта qemu
и Apache веб-расширения, ни прокси, ни WAF, ни клиентской библиотеки.

Вывод: дефект платформы/веб-расширения на этом билде. До исправления
**полагаться на штатную оптимистическую блокировку нельзя**.

### Что сделано и чего это не решает

`odatatest_update_entity()` перед записью перечитывает документ и сравнивает
`DataVersion` с тем, что ушёл в форму; при расхождении запись не выполняется.
`If-Match` продолжаем слать — он безвреден и заработает, если платформу починят.

Это НЕ атомарно: между проверкой и `PATCH` остаётся окно гонки (TOCTOU).
Ловится реальный сценарий «пока заполняли форму, документ изменили в 1С»;
две одновременные записи — нет.

### Архитектурное следствие для табличных частей

Стандартный OData требует передавать табличную часть целиком (replace
collection), построчного PATCH нет. При рабочем `If-Match` это безопасно:
версия объекта охватывает и табличные части, конкурентная замена получает 412.
При неработающем `If-Match` **гарантированного способа не потерять чужие
строки в рамках стандартного OData не существует**.

Корректное решение (отложено, за пределами демо): собственный HTTP-сервис в
расширении, который в ОДНОЙ транзакции ставит управляемую блокировку, читает
объект, сверяет версию, применяет изменение и фиксирует; плюс `operationId`
для идемпотентности повторов. Дополнительно: `LineNumber` нестабилен
(меняется при вставке/удалении/сортировке), поэтому построчные команды
требуют собственного UUID-реквизита строки.

Отдельно: `If-Match` документирован только для `PATCH`/`DELETE`; для
`POST .../Post` и `.../Unpost` (проведение) такой защиты не обещано вообще.

### Что стоит проверить, когда дойдут руки

1. повторить на справочнике и на документе без табличной части;
2. повторить без заголовка `1C_OData-DataLoadMode`;
3. повторить на актуальном билде платформы, поддерживаемом для этого релиза BAS;
4. если валидный устаревший токен всё равно даёт 200 — оформить reproducer
   (версия и билд платформы, тип базы, СУБД, четыре запроса и ответы).

## `$expand` не работает при запросе одиночной сущности

`Document_X(guid'...')?$expand=Организация` -> `"Опція $expand не підтримується
у разі запиту одиночних сутностей"`. Поэтому карточка читает документ как
коллекцию из одной строки с `$filter=Ref_Key eq guid'...'` -- там `$expand`
работает, и представления ссылок обходятся одним запросом вместо запроса
на каждый реквизит.

## Клиент `dakword/odata1c-client` отвергает реальные ссылки 1С

`Query::get($guid)` валидирует ссылку регуляркой RFC 4122: четвёртая группа
обязана начинаться с `0|8|9|a|b`. 1С этого варианта не соблюдает -- реальная
ссылка `f7fd3b80-a643-11ea-1e9b-0800272f5ce8` отвергается с `GUID_WRONG`.
Патчить `vendor/` нельзя (им управляет composer), поэтому запросы одиночных
документов собираются напрямую через `request()`.

## Запись через OData перегенерирует номер документа (решено, но знать обязательно)

Обнаружено случайно при чтении табличной части: у документа, который я
правил через OData, номер оказался `0000-000001` вместо `ТП00-000001`.
У соседних документов, которых запись не касалась, префикс на месте
(`РС00-000001`, `РС00-000002`, ...). То есть префикс потерял ровно тот
документ, который записывали.

Механика: `PATCH` даже одного поля (`{"Комментарий": "..."}`) заставляет
платформу перезаписать объект целиком, отрабатывают обработчики БСП
(префиксация объектов), и номер формируется заново -- без префикса.

Обход, проверенный на живой ИБ: передавать `Number` в payload явно, даже
если поле не редактируется. Тогда номер сохраняется.

Сделано: форма карточки всегда отправляет скрытое поле `document_number`,
а `$payload['Number']` подставляется в каждый `PATCH`.

Следствие шире демо: любая интеграция, которая пишет в документы 1С через
стандартный OData "только одно поле", обязана передавать и все реквизиты,
которые конфигурация умеет пересчитывать при записи. Иначе тихая порча
данных. Что именно пересчитывается -- зависит от конфигурации; для BAS ERP
здесь это как минимум номер.

Испорченный в ходе экспериментов номер восстановлен обратно в `ТП00-000001`.

### Продолжение (2026-08-28): обход не спасает при смене организации -- коллизия номеров

Проверено на живой ИБ вместе с починкой выпадающих списков справочников
(см. `README.md`/коммит про `ajax_autocompleter`). Обход выше ("всегда
передавать `Number`") держит номер только пока состав изменяемых полей не
трогает **организацию** документа. Как только `Организация_Key` в payload
меняется (в любую сторону, включая обратно на пустую ссылку), платформа
пересчитывает номер по нумератору, привязанному к организации, ИГНОРИРУЯ
явно переданный `Number`:

```
1) ТП00-000001, Организация = <пусто>
2) PATCH Организация_Key = <РОССА, ВК ТОВ>, Number = "ТП00-000001" (as is)
   -> платформа сама записала Number = "РС00-000001"
```

Опасность конкретно в этом случае: `РС00-000001` уже существовал у другого,
несвязанного документа в этой же копии базы -- получилась коллизия номеров
между двумя разными объектами. Обнаружено и исправлено в течение той же
сессии (лишний документ вернул обратно пустую организацию и явный
`Number`), но сам факт стоит держать в голове: **нумератор в BAS ERP
привязан к организации и пересчитывается при её смене независимо от того,
что передано в `Number`**. Общий обход ("передавать Number") защищает только
от порчи номера при правках, не трогающих организацию.

Практический вывод для любых будущих живых тестов на этой копии: менять
`Организация_Key` через OData на реальных документах, у которых уже есть
"нормальный" номер с префиксом, нужно с оглядкой -- после смены нельзя
полагаться на переданный `Number`, следует сразу перечитать документ и
проверить номер на коллизию с другими документами того же вида, прежде чем
продолжать эксперимент.

Воспроизведено ЕЩЁ РАЗ в той же сессии, уже другим клиентским кодом --
после замены `ajax_autocompleter` на настоящий `<select>`/select2 для
маленьких справочников (см. `README.md`). Значит дело не в конкретном
PHP-виджете и не в форме запроса: любой `PATCH`, меняющий
`Организация_Key`, независимо от того, как именно собран payload,
получает тот же пересчёт номера платформой. Это подтверждает вывод выше как
свойство платформы/конфигурации, а не артефакт конкретной реализации формы.

## Добавление строк табличной части: что 1С принимает

Проверено на живой ИБ: новая строка принимается с МИНИМАЛЬНЫМ набором --
`LineNumber` плюс те реквизиты, что есть на форме. Остальные платформа
заполняет значениями по умолчанию (`Упаковка_Key` пришёл нулевым GUID).

То есть добавление через веб технически работает, но семантически строка
получается неполной: в BAS ERP у строки заказа обычно есть упаковка, вид цены,
ставка НДС, и «пустые» значения могут быть некорректны для проведения и
последующего учёта.

Для демо этого достаточно. Для реальной интеграции нужно либо выводить эти
реквизиты на форму, либо заполнять их серверной логикой 1С (что снова
означает собственный HTTP-сервис, а не стандартный OData).

## Создание документов через OData падает: обработчик `ОбработкаЗаполнения`

Проверено на живой ИБ (2026-08-27) для трёх типов -- `ЗаказПоставщику`,
`ВыпускПродукции`, `МаршрутныйЛистПроизводства`. Любой `POST`, даже
минимальный, отвечает одинаково:

```
POST Document_ЗаказПоставщику   {"Date":"2026-08-27T12:00:00"}
-> HTTP 500
   "Помилка при виконанні обробника - 'ОбработкаЗаполнения'"
```

Payload при этом роли не играет: с организацией и без, с комментарием и без --
результат один. Значит дело не в составе реквизитов, а в том, что обработчик
заполнения конфигурации не отрабатывает в контексте нашего OData-сеанса.

Наиболее вероятная причина -- тот же класс проблем, что и у
`ПоступлениеТоваровУслуг` (HTTP 500 на чтение): пользователь `autosetup-odata`
имеет минимальный набор статических ролей и не входит ни в одну группу
доступа, поэтому код БСП/ERP, читающий настройки пользователя и значения
по умолчанию, падает.

Что делать дальше (не сделано):

1. посмотреть журнал регистрации 1С -- там должна быть строка с реальным
   исключением внутри `ОбработкаЗаполнения`;
2. проверить, лечится ли это добавлением ролей (например, чтения настроек
   пользователя) или заведением группы доступа;
3. если нет -- создание документов этого класса через стандартный OData
   в этой конфигурации невозможно, и остаётся собственный HTTP-сервис.

Форма создания в модуле реализована и показывает реальную ошибку 1С -- это
и есть полезный результат эксперимента, а не заглушка.

## Физическое удаление: реализовано, но вживую не проверялось

Причина простая и осознанная: создать одноразовый документ нельзя (см. выше),
а удалять безвозвратно реальный документ из копии продакшена ради теста --
неоправданно. Пометка удаления и её снятие проверены вживую и обратимы.

## Объединение `card_page.js`/`runtime_lib.js` с `dol_object_form.js` через `entity_source` — отложено

Вопрос, который стоило явно закрыть при вливании расшивки `dol_table_layout.js`
в dobaerp (см. `doc/merge-back.md`): если для таблицы источник строк вынесли
в подставляемый `row_source` (SQL / 1С OData), почему для карточки документа
не сделать то же самое с `dobaerp/src/idiomlib/dol_object_form.js` — завести
`entity_source` и переиспользовать один генератор формы вместо двух
параллельных (`dol_object_form.js` для SQL-объектов и наш
`src/php/card_page.js` для OData-документа)?

### Почему не сделано сейчас

У `dol_table_layout.js` был один узкий, самодостаточный шов: «дай мне
строки + total count, постранично» (`gen_search`/`gen_fetch`/`gen_row_next`/
`gen_free`). Ничего, что происходит со строкой дальше (рендер колонок), этот
шов не касался — поэтому вынос был чисто механическим и доказан побайтовым
паритетом всего сгенерированного вывода WMS и BPM.

У `dol_object_form.js` (1541 строка) такого шва нет — доступ к данным
просачивается по всему файлу, а не сосредоточен в одной точке:

* доступ к БД вшит прямо в шаблоны отдельных типов полей, например тип
  `sql_enum` делает `$db->query("SELECT ... WHERE rowid = " . $object->...)`
  внутри собственного PHP-шаблона — таких мест несколько, каждое со своей
  формой SQL;
* весь файл держится на контракте Dolibarr `CommonObject`: `$object->fetch()`,
  `$object->update($user)`, `$object->create($user)`, триггеры, хуки,
  extrafields, `rowid`. У OData-документа 1С этого нет и быть не может —
  это не «другой источник тех же операций», это другая модель объекта.

У `dobaerp/src/idiomlib/dol_table_element.js` (табличная часть, 1975 строк)
та же вшитость доступа к данным, плюс ещё и другая модель конкурентности:
построчный CRUD в БД (add/update/delete конкретной строки по `rowid`)
против OData, где стандартный интерфейс 1С требует прислать всю табличную
часть целиком (replace collection) — построчного PATCH не существует.

Чтобы сюда добавить `entity_source` по образцу `row_source`, пришлось бы
переписывать заметную часть этих ~3500 строк, вынося доступ к данным из
каждого field-kind шаблона по отдельности — и, в отличие от
`dol_row_source_*`, такой рефактор нельзя доказать побайтовым паритетом,
потому что реально меняется поведение (сейчас его нет вообще), а не просто
переносится код. Это не мержбэк уже готового решения, а отдельный, заметно
больший проект по редизайну `dol_object_form.js`/`dol_table_element.js`,
не имеющий отношения к задаче демо. Независимо к тому же выводу пришло и
собственное исследование готовых решений (`doc/auto-doc-edit.md`): готового
1С-специфичного редактора объектов по `$metadata` не существует, а для
честного обобщения нужна отдельная модель вроде JSON Forms, а не точечная
правка существующего генератора.

### Что уже сделано правильно и облегчит объединение в будущем

`card_page.js` (генерация PHP-разметки формы) и `runtime_lib.js` (доступ к
1С OData: `odatatest_fetch_entity`/`odatatest_update_entity`/
`odatatest_table_payload`/...) уже разделены — в том же духе, что и
`row_source`: рендер отдельно, доступ к данным отдельно. Просто сегодня эта
пара самостоятельна и ни к чему не подключается как источник. Если/когда в
`dol_object_form.js` появится собственная `entity_source`-абстракция (по
инициативе и на материале самого dobaerp, не этого демо), `runtime_lib.js`
уже готов стать для неё конкретной реализацией без переписывания с нуля.

### Условие возврата к теме

Не раньше, чем в dobaerp появится собственная, dobaerp-native причина
разделить `dol_object_form.js`/`dol_table_element.js` на рендер и источник
данных (например, второй SQL-источник данных для формы, а не только для
таблицы). Пока единственный потребитель гипотетической абстракции — этот
демо-проект, попытка её спроектировать заранее — ровно тот костыль
«под один случай», который правила проекта запрещают.
