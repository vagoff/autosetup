# Обратное вливание в dobaerp

Форк запрещён. Изначально мы держали у себя копии нескольких модулей
dobaerp, потому что расшивали их от SQL; эти копии обязаны были вернуться
в dobaerp как обычные правки. Сделано.

## Что было влито

| Файл dobaerp | Что сделано |
|---|---|
| `src/idiomlib/dol_table_layout.js` | выборка строк вынесена в подставляемый источник (`get_table_row_source()` / `set_table_row_source()`), источник можно задать в декларации страницы через `row_source` |
| `src/idiomlib/dol_row_source_sql.js` | **новый**: SQL-источник, дословный перенос вынесенного кода |
| `src/idiomlib/dol_row_source_odata.js` | **новый**: источник строк на 1С OData; ни строчки специфики этого проекта, переносился как есть |

Локальных копий `src/idiomlib/dol_table_layout.js`, `dol_row_source_sql.js`,
`dol_row_source_odata.js` в этом проекте больше нет — генератор
(`scripts/generate-odatatest-module.js`, `src/odatatest_app_data.js`) берёт
их из dobaerp напрямую (`../idiomlib/...`, резолвится через
`dobaerp/src/interlink/mixins_linker.js`, либо абсолютным путём — так же,
как остальные dobaerp-модули, которые этот генератор всегда использовал без
локальных копий).

## `dol_module.js` / `dol_templates.js` — влиты независимо, другим путём

К моменту, когда дошли руки до этого мержа, в dobaerp это уже было сделано
— независимо, в рамках работы над модулем `BPM` (`src/bpm/bpm_genmod.js`).
API получился не тот, что предполагался изначально в этом проекте:

* `generate_module_class(site_dir, m_info)` → **`generate_module_descriptor(site_dir, m_info)`**;
* `m_info.module_dir` убран: каталог модуля выводится из `m_info.module_name`
  (нижний регистр), передавать отдельно больше не нужно;
* `m_info.rights` сменил форму: было `{code, label}`, стало
  `{label, type, default, shortname}` — `type` это `'r'/'w'/'d'` (для
  наглядности дескриптора), `default` решает, выдаётся ли право
  автоматически при активации модуля, `shortname` — то, что видит
  `$user->hasRight(module, shortname)` в PHP. У нас это по-прежнему
  `read`/`write`/`delete`, изменилась только форма объекта в конфиге
  (см. `data/gen-config.json5#module.rights`);
* формат хранения прав в сгенерированном классе модуля тоже другой и более
  правильный: `$this->rights[$r][0] = $this->numero . sprintf('%02d', $r)`
  вместо `$this->numero + index` — это стандартная для Dolibarr схема ID
  прав, а не наша прежняя.

Проверено на живом стенде: `modODataTest.class.php` — единственный файл,
который меняется при переходе на актуальный API dobaerp (новые ID прав);
все страницы списков и карточек документов остались побайтово теми же, что
были в утверждённом манифесте (`node --test src/tests/php-odata-demo-generation.test.js`).

Практический вывод для будущих сессий: если локальная копия правки для
dobaerp лежит у нас дольше одной сессии, апстрим может уехать сам по себе
(там работают и над другими модулями), и его API может поменяться не так,
как мы предполагали при форке. Единственная защита — не тянуть с вливанием.

## Что осталось намеренно локальным — и почему это не то же самое

`src/php/card_page.js` (генератор PHP-карточки документа) и
`src/php/runtime_lib.js` (доступ к 1С OData: CAS по `DataVersion`,
replace-collection табличных частей, обходы конкретных багов платформы) —
**не переезжают в dobaerp**. Это не тот же случай, что `dol_table_layout.js`:

* у `dol_table_layout.js` был один узкий шов (строки + total count постранично),
  вынос был чисто механическим и доказан побайтовым паритетом;
* у `dobaerp/src/idiomlib/dol_object_form.js` (аналог для карточки/формы
  объекта) такого шва нет: доступ к БД вшит прямо в шаблоны конкретных
  типов полей (например, `sql_enum` делает `$db->query(...)` внутри
  собственного рендер-шаблона), а весь файл держится на контракте Dolibarr
  `CommonObject` (`fetch/update/create/delete`, триггеры, хуки,
  extrafields, `rowid`) — которого у OData-документа 1С нет и не может
  быть. У `dol_table_element.js` (табличная часть) та же вшитость плюс ещё
  и другая модель конкурентности: построчный CRUD в БД против
  OData-требования отправлять всю табличную часть целиком.

Подробнее — в `doc/deferred-todo.md#Объединение card_page.js` -- там же
условие, при котором к этому стоит вернуться.

## Порядок (справочно, на случай следующего такого мержа)

1. Сверить исходники: не отошли ли реальные dobaerp-файлы от того, от чего
   форкались (побайтовое сравнение с `upstream/*.orig`, если файл уже
   расшивался, либо чтение истории/использования, если нет).
2. Наложить/добавить файлы прямо в `dobaerp/src/idiomlib/`.
3. Прогнать регенерацию всех приложений dobaerp, которые используют
   изменённый idiom (`node src/wms/wms_app_gen.js`, `node src/bpm/bpm_app_gen.js`,
   ...), сравнив хэши сгенерированного дерева до/после правки. Расхождений
   быть не должно -- если есть, значит правка не behavior-preserving.
4. В своём генераторе (`generate-odatatest-module.js`,
   `odatatest_app_data.js`) убрать локальные копии и указать на dobaerp
   напрямую.
5. Перегенерировать свой модуль и свериться со своим утверждённым
   манифестом (`node --test src/tests/php-odata-demo-generation.test.js`).
   Расхождения объяснимы только тем, что реально изменилось в API dobaerp
   (как с `dol_module.js` выше) -- не больше.
